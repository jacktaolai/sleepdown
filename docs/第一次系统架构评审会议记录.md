## 二、过度设计识别与简化建议

### 1. 分层架构过重 → 合并领域层与应用层

**现状**：严格区分了`Domain Layer`（实体、Repository接口）和`Application Layer`（UseCase、Providers），中间还有`Data Layer`的实现隔离。

**问题**：对于MVP阶段，业务逻辑简单（主要是CRUD和基本计算），无需如此严格的分层。引入过多的抽象（Repository接口、UseCase类）会增加代码量和理解成本，降低开发速度。

**建议**：
- 合并`domain`和`application`，将业务逻辑直接放在`Provider`或`Controller`中。
- 暂时去掉`Repository`接口，直接让`Provider`调用`Data Layer`的数据库操作。后续如果需要切换数据源（如从本地到云端），再提取接口重构。
- UseCase 可用简单的Provider方法替代，例如在`courseListProvider`中直接包含`addCourse`逻辑，无需独立`AddCourse`类。

### 2. 状态管理选型过重 → 使用更轻量的Provider或GetX

**现状**：选用Riverpod，并设计了多个`StateNotifierProvider`。

**问题**：Riverpod功能强大，但学习曲线和代码量相对较高。MVP阶段可以选用更简单的方案，如`Provider`（来自官方provider包）或`GetX`，它们能快速实现状态共享和更新。

**建议**：
- 使用`Provider`或`ChangeNotifierProvider`配合`ChangeNotifier`，足以应对课程列表、当前周次等状态。
- 若团队熟悉Riverpod，也可保留，但不必过度使用`StateNotifier`，可先用`StateProvider`简化。

### 3. 导入导出功能过早引入 → 延迟到后续迭代

**现状**：设计了`ImportPage`、`CSV导入`、`Web导入`等模块，包含`CourseParser`接口和多种实现。

**问题**：MVP阶段只需要手动添加课程，导入功能属于“高级功能”，不应在初期版本实现。这会分散精力，且增加代码维护量。

**建议**：
- 彻底移除`ImportPage`、`ImportDialog`及相关解析器代码。
- 删除`web_parsers`目录、`CsvCourseParser`等。
- 保留`ExportToCSV`？MVP未要求导出，也可移除。

### 4. 平台小组件设计过细 → 统一使用home_widget插件

**现状**：为iOS、Android、鸿蒙分别设计了不同的适配方案（WidgetKit、AppWidgetProvider、Form Link），并规划了平台通道。

**问题**：MVP只需基础小组件（如显示今日课程），而且“基础小组件”可能指应用内的小部件（如课程卡片），而非桌面小组件。即使需要桌面小组件，也应使用成熟的Flutter插件（如`home_widget`）统一处理，避免手写平台代码。

**建议**：
- 明确“基础小组件”是应用内组件还是桌面小组件。若是桌面小组件，使用`home_widget`插件即可，它通过共享存储（UserDefaults/SharedPreferences）实现数据传递，无需为各平台单独写原生代码。
- 删除`platform/`目录下的原生代码设计，保留简单的平台通道备用。

### 5. 目录结构过于复杂 → 按MVP功能精简

**现状**：文档列出了庞大的目录树，包含`core`、`domain`、`data`、`application`、`presentation`、`platform`等多个顶层目录，每个目录下还有多层子目录。

**问题**：MVP代码量少，无需如此复杂的结构。过多的文件夹会增加导航成本，让新手困惑。

**建议**：采用更扁平的目录结构，例如：

```
lib/
├── main.dart
├── models/                # 实体类（Course, WeekPattern, TimeSchedule）
├── providers/             # 状态管理（简单Provider）
├── screens/               # 页面（Home, CourseDetail, CourseEdit, Settings, TimeSettings）
├── widgets/               # 通用组件（CourseCard, WeekSelector, ScheduleGrid）
├── utils/                 # 工具类（WeekCalculator, DateUtils）
└── database/              # 数据库操作（DBHelper, DAO）
```

待功能稳定后，再根据实际复杂度重构为分层结构。

### 6. 数据库设计可能过重 → 评估是否真的需要SQLite

**现状**：使用sqflite，设计了courses、time_schedules、settings三张表，并创建索引。

**问题**：MVP数据量小，课程数量有限，用SQLite是否必要？也许`shared_preferences`+JSON文件即可满足需求。

**建议**：
- 初期使用`shared_preferences`存储课程列表（序列化为JSON），简化开发。
- 若担心性能或后续扩展，可保留SQLite，但不必预先创建所有索引，可先不加索引，待数据量增大后再优化。
- `time_schedules`表：MVP可能只需要一套作息时间，可考虑直接存在`settings`表中，不必单独建表。

### 7. 周次模式解析过度设计 → 先支持简单模式

**现状**：设计了`WeekPattern`、`WeekRange`、`WeekType`，并提供了复杂的解析逻辑（支持“1-5、7-11单、12-16双”）。

**问题**：MVP阶段手动添加课程时，用户可能只需输入简单的周次范围（如“1-16”），甚至无需区分单双周。解析复杂周次模式会增加代码复杂度。

**建议**：
- 简化周次模型：只支持连续周次范围（如1-16），用两个整数`weekStart`和`weekEnd`表示。若后续用户反馈需要单双周，再扩展。
- 如果必须支持单双周，可先用简单的字符串存储，解析逻辑后续实现。

#### 2. 简化 WeekPattern

// MVP 简化版
class WeekPattern {
  final int startWeek;
  final int endWeek;
  final bool isOddOnly;   // 单周
  final bool isEvenOnly;  // 双周
  
  bool contains(int week) {
    if (week < startWeek || week > endWeek) return false;
    if (isOddOnly && week % 2 == 0) return false;
    if (isEvenOnly && week % 2 == 1) return false;
    return true;
  }
}

gemini:
你好！作为团队的系统架构师，我仔细阅读了这份《Sleepdown 系统架构设计文档》。

总体来说，这份文档逻辑清晰、技术栈选型前沿（如 Riverpod），且对平台特性的考虑比较全面。但是，结合我们“开源快速迭代”以及“MVP阶段”的定位，当前的架构方案明显存在过度设计（Over-engineering）的问题。为了保证我们能快速跑通第一版并推向市场，我们需要对架构进行“瘦身”。

以下是我的详细审核意见和建设性调整方案：

一、 关于“过度设计”的重点打回与精简建议

对于一个 MVP 阶段的纯本地工具类 App，当前的架构太“重”了。严格遵循经典的 Clean Architecture（四层架构）会产生大量的样板代码（Boilerplate），严重拖慢迭代速度。

1. 砍掉 Application 层的 UseCase

当前问题：文档中设计了独立的 UseCase 层（如 AddCourse, GetWeekCourses）。在 Flutter + Riverpod 的生态中，引入 UseCase 纯属脱裤子放屁。

修改建议：直接让 Riverpod 的 Notifier 充当 ViewModel/UseCase 的角色。UI 触发 CourseListNotifier.addCourse()，该方法内部直接调用 CourseRepository。这足以保持业务逻辑和 UI 的解耦。

2. 砍掉 Domain 层和 Data 层的 Entity/Model 互相转换

当前问题：按文档目录，存在 domain/entities/course.dart 和 data/models/course_model.dart。对于一个以本地存储为主的 App，维护两套长得几乎一样的数据类，并在 Repository 中做 mapper 转换，简直是噩梦。

修改建议：合二为一。使用单个数据类（建议结合 freezed 或直接定义），既作为内存状态实体，也作为本地存储映射。

3. 暂缓 Parser 接口和多数据源设计

当前问题：文档在 Domain 层设计了高度抽象的 CourseParser、WebParser，并规划了 CSV 解析等。但回顾 Phase 1 - MVP 需求，只要求“手动添加/编辑课程”。

修改建议：严格遵循 YAGNI 原则（You Aren't Gonna Need It）。MVP 阶段直接删掉所有与网络导入、CSV解析相关的代码设计。这些功能留到 Phase 3 或 4 再建文件夹不迟。

4. 放弃“按层分包”，改为“按功能分包 (Feature-first)”

当前问题：目前的目录结构是 presentation, domain, data 等。这意味着开发者加一个“课程备注”字段，需要跨越 4 个大文件夹改 5 个文件，开发体验极差。

修改建议：按功能模块划分。例如：

code
Text
download
content_copy
expand_less
lib/
├── core/               # 通用工具、主题、数据库配置
├── features/
│   ├── course/         # 课程相关的所有内容都在这
│   │   ├── domain/     # (Course 类)
│   │   ├── data/       # (CourseRepository 类)
│   │   ├── providers/  # (Riverpod Notifiers)
│   │   └── presentation/ # (各种页面和组件)
│   ├── schedule/       # 周视图与日视图展示
│   └── settings/       # 设置与时间节次配置
二、 针对 PO 级 MVP 需求的合理性审核

对照 MVP 需求（周视图、手动增删改、自定义节次、课程详情、基础小组件），整体满足，但有几个核心技术细节需要调整：

1. 数据库选型：强烈建议将 sqflite 替换为 Isar 或 Hive

痛点：文档使用 sqflite。对于课程表应用，经常需要存储复杂的嵌套结构（如 WeekPattern、TimeSlot）。在 SQLite 中，你要么把它们序列化为 JSON String 存入 TEXT 字段（查询困难），要么建多张关联表（查询繁琐）。

架构师建议：这是一款离线优先的快速迭代产品，建议使用 Isar Database（目前 Flutter 生态最强的本地 NoSQL）。它支持直接存储 Dart 对象、原生支持复杂条件查询、且性能极高，能帮你省去 80% 的 SQL 拼接和 JSON 解析代码。

2. 数据模型 (Course) 遗漏了 UI 强相关字段

痛点：用户排课时，给课程分配不同的颜色是强需求（也是周视图好看的关键）。当前的 Course 实体没有颜色标记。另外也没有标明该课程属于哪一个学期或哪一个时间表。

架构师建议：

在 Course 实体中增加 colorValue (int) 或 themeIndex。

在 Course 中增加 semesterId 或 scheduleId（如果不加，以后一旦用户有多个学期的数据，查询就会全乱套）。

3. 平台小组件（Widget）的预期管理

建议：文档提到了鸿蒙卡片（Form Link）。由于目前 Ohos-Flutter 还在发展期，Platform Channel 联通鸿蒙原生卡片的坑非常深。为了确保 MVP 能在一个 Sprint 内上线，MVP 阶段的小组件必须缩减为仅支持 iOS 和 Android，鸿蒙仅保证 App 本身能运行即可。

4. 自定义节次时间（TimeSchedule）的设计风险

提醒：TimeSchedule 设计了 slots。在业务逻辑（应用层）中，务必增加时间冲突校验。比如第一节课 08:00-08:45，第二节课不能早于 08:45 开始。这个逻辑需要放在 SettingsNotifier 中进行拦截，文档中未体现这种校验逻辑的位置。

三、 总结：架构师给出的 MVP 重构方案蓝图

为了实现**“快速启动、最小化实现、易于迭代”**，建议你的最终架构形态如下：

分层：简化为 3 层：Presentation (UI) -> Application (Riverpod Notifiers) -> Data (Isar + Repositories)。

数据：使用 Isar 数据库，直接使用一套带 Isar 注解的 Data Class。

功能：剔除所有 Import/Export/Parser 的设计，专注做好 CRUD 和时间周次计算算法（WeekCalculator）。

## 八、最终建议决策

### ✅ 确认采纳（高优先级）

1. **删除 UseCase 层** - 业务逻辑放入 StateNotifier
2. **简化为三层架构** - UI → Logic(Riverpod) → Data
3. **删除 RemoteDataSource 和 FileDataSource**
4. **删除 Parser Interface 及相关实现**
5. **删除 DayViewPage 和 ImportPage**
6. **删除 ImportDialog 组件**
7. **简化 WeekPattern 模型**
8. **合并 Entity 和 Model**
9. **删除鸿蒙小组件适配**
10. **目录结构扁平化/按功能分包**
11. **删除冗余依赖（dio、path_provider）**

### ⚠️ 建议采纳（中优先级）

12. **Course 实体增加颜色字段** - UI强需求，成本低
13. **删除国际化模块** - MVP只做中文
14. **增加时间冲突校验逻辑** - 防止脏数据
15. **统一使用 home_widget 插件** - 简化小组件开发

### ❌ 暂不采纳

16. **状态管理改用 Provider/GetX** - 保留 Riverpod（3/4反对）
17. **数据库改用 shared_preferences** - 保留 SQLite（性能和扩展性考虑）
18. **数据库改用 Isar/Hive** - 后续讨论（学习成本）
